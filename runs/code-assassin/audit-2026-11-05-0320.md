**FINDING 1** — `[ILOGIC]` v2.2.9

**Line ~1150–1210 (Drawing Relink section + F1 Finally)**

**Summary:** FIX E creates a benign double-close of `oDwgR`, and on a save failure, the drawing is silently closed by the F1 Finally block, discarding in-memory relink changes with no additional user warning beyond the log entry.

**Detail:**
- FIX E adds `oDwgR` to `oProvRebuildOpened` so the F1 Finally block closes it on failure.
- On the success path (`bDwgOpenedHere AndAlso bDwgSaved = True`), `oDwgR` is explicitly closed in the Drawing Relink section, **and** the F1 Finally also calls `Close(True)` on it via `oProvRebuildOpened`. The Try/Catch in Finally absorbs the error — no crash — but it is a logical double-close.
- On the **failure path** (`bDwgSaved = False`): the Drawing Relink section leaves `oDwgR` open, but the F1 Finally closes it via `Close(True)` (discard mode). The in-memory FD replacements are silently lost. The user sees `DWG-SAVE-FAIL` in the log but receives no notice that the document was auto-closed.

**Suggested fix:**
```vb
' In Drawing Relink close block — remove from oProvRebuildOpened after explicit close:
If bDwgOpenedHere AndAlso bDwgSaved Then
    Try : oDwgR.Close(True) : Catch : End Try
    oProvRebuildOpened.Remove(oDwgR)   ' prevent double-close in Finally
End If
' For the failure case, leave oDwgR in oProvRebuildOpened so Finally closes it,
' but add a log line noting the document was auto-closed with unsaved changes:
' e.g. "DWG-AUTO-CLOSED-UNSAVED: drawing closed by cleanup; relink changes lost."
```

**FINDING 2** — `[ILOGIC]` v2.2.9

**Line ~558 (Phase 4, `bGAOpenedHere` close path)**

**Summary:** If Phase 4 GA save fails and `bGAOpenedHere = True`, the new GA is closed unconditionally with `Close(False)`, silently discarding all Phase 4 occurrence-replacement changes.

**Detail:**
```vb
Try
    oNewGA.Save2(False)
    ...log P4-GA-SAVED...
Catch exGASave
    ...log P4-GA-SAVE-FAIL...
End Try
...
If bGAOpenedHere Then
    Try : oNewGA.Close(False) : Catch : End Try   ' ← always runs, even after save failure
End If
```
Compare to Phase 3 behaviour where on save failure the document is explicitly left open ("left open for retry"). Phase 4 doesn't follow this pattern.

**Suggested fix:** Track whether the GA save succeeded and only close on success:
```vb
Dim bGASaved As Boolean = False
Try
    oNewGA.Save2(False)
    bGASaved = True
    ...
Catch exGASave ...
End Try
If bGAOpenedHere AndAlso bGASaved Then
    Try : oNewGA.Close(False) : Catch : End Try
End If
' If save failed, leave the GA open so the user can manually save.
```

**FINDING 3** — `[ILOGIC]` v2.2.10

**Line ~490–497 (Phase 2 key ordering, v2.2.10 GA-first block)**

**Summary:** `List(Of String).Remove` uses case-sensitive comparison, but `oRenameMap` was created with `StringComparer.OrdinalIgnoreCase`. On a path whose casing in the Dictionary key differs from `sTopFull`, `Remove` silently fails and `Insert(0, sTopFull)` adds a duplicate entry — causing the GA to be processed twice by Phase 2.

**Detail:**
```vb
If oRenameMap.ContainsKey(sTopFull) Then   ' case-insensitive — may find key stored differently
    oMapKeys.Remove(sTopFull)              ' case-SENSITIVE — may NOT remove the stored key
    oMapKeys.Insert(0, sTopFull)           ' inserts a duplicate if Remove failed
```
On Windows, `oDoc.FullFileName` returns consistent casing from Inventor, so this is a low-probability edge case. When it fires, the GA's second processing hits `IsAlreadyProcessed` → PROV-SKIP — no crash, no incorrect output, just an extra disk open/check cycle.

**Suggested fix:** Use a case-insensitive Remove:
```vb
' Case-insensitive Remove
Dim iTopIdx As Integer = oMapKeys.FindIndex(
    Function(k) String.Compare(k, sTopFull, StringComparison.OrdinalIgnoreCase) = 0)
If iTopIdx >= 0 Then oMapKeys.RemoveAt(iTopIdx)
oMapKeys.Insert(0, sTopFull)
```
