# BEEXCITED HIVE MIND — Cross-Project Architecture & Session Sync
**Status:** Working architecture / MU-directed principles; implementation unverified. **Updated:** 2026-11-12.
**Canonical discussion:** [PWTP issue #8](https://github.com/Waynitos/MAD-SSSOT/issues/8).
**Existing launch protocol:** [PROJECT-LAUNCH-Plus.md](../PROJECT-LAUNCH-Plus.md). **MAD framework:** [README.md](../README.md).

## Purpose
All BEEXCITED projects and new sessions should share the latest relevant **MU-approved direction**, while keeping individual project baselines, code, issues and evidence separate. A chat is not the SSSOT. Never claim that an unbuilt orchestration feature already operates.

## MU-established principles
1. **Outcome first:** Processes serve good results; simplify, combine or retire those that add unnecessary friction, while retaining necessary safety, evidence and accountability.
2. **BBⁿ — Beyond Better:** Continually seek practically achievable improvements. Every real project is both delivery work and evidence for improving the system.
3. **HIVE MIND:** A coordinated specialist swarm with shared purpose and learning, not uncritical herd/groupthink. MAD preserves challenge and independent scrutiny.
4. **Path-Aligned Autonomy:** Proven, authorised processes enable work to proceed without repeated MU direction. Agents may improve **how** to reach the approved destination, not silently change the destination, scope, safety boundaries or strategic intent. During pilots, MU explicitly clears Departure.
5. **Minimum effective workflow:** Select only phases, agents, checks and gates justified by the task's risk and needs; do not impose every standard phase mechanically.
6. **Evidence before institutionalisation:** Actual projects reveal essential, redundant, missing and beneficial processes. Proposed improvements need verification before becoming global defaults.
7. **Specialist lanes:** Clear ownership and job descriptions; avoid permanent role overlap. Temporary authorised coverage may prevent unnecessary blocking.

## Project flow — provisional; reconcile with existing Launching Pad naming
FRONT DESK (single MU entry) → PTP (Task Path: intake, clarifying questions, initial research, routing) → PROJECT ARRIVAL / BOARDING LOUNGE (PM drafts roadmap, agent requirements and sprints) → BOARDING CALL (PWTP agenda begins) → PWTP (POW WOW TRANSIT PROCESS: MU-agent brainstorming, design, prototyping, evidence, MAD, adaptive sprint closures) → DEPARTURE READINESS (flight-leg package and MU pilot approval) → DEPARTURE (approved execution flight leg) → execution/validation/blackbox feedback; material new discoveries may trigger reboarding/new PWTP leg.
Bounded routine tasks may stay on PTP and bypass PWTP.

## Adaptive Project Flight Plan
- **Project roadmap:** Candidate future flight legs, provisional dependencies and needed capabilities.
- **Current flight-leg plan:** Approved destination, scope, exclusions, roster, permissions, risks and departure gate.
- **Sprint Flight Cards:** Owner, MU input, prerequisites, deliverable, measurable closure, evidence, status and decisions.
- **Flight blackbox:** Planned vs actual, decisions, changes, MAD findings, MU tests, regressions, lessons, next action, version/commit, and cross-project reuse candidate.
- PM can reorganise authorised methods, but significant redirection returns to MU. Future legs remain proposals until authorised.

## Workforce / agent architecture — responsibilities to reconcile, NOT a final org chart
- **HR Agent (proposed):** Detect unmet capability needs, inspect agent registry and job descriptions, assess reuse vs recruitment, initiate specialist creation/assignment when authorised.
- **Agent development/training/validation function (name not confirmed):** Define competence criteria, test proposed agents, verify before deployment; creating an agent is not proof of competence.
- **Project Manager:** Plan, coordinate, track milestones and flight legs, maintain closure evidence, identify gaps.
- **PTP / ROUTE-001 (naming to verify):** Select task-appropriate route and initial workflow/roster.
- **Slayer (historically discussed; remit unverified):** Possible process-efficiency/oversight function; do not assign final authority without source reconciliation.
- **Thrasher / Prince of Projects (historically discussed; remit unverified):** Reconcile before activation.
- **MAD AA / DA / SSA:** Advocacy, independent challenge, synthesis.
- **MAD Super Agent (SA):** Existing README says it researches latest MAD methods and evolves MAD when triggered. The MU recalls debate-argument completeness (e.g. warranty/material in product review); reconcile exact remit, do not assume SA owns general process cleanup.
Agent hiring should not proliferate agents by default: verify capability gap, need, authority, cost/overhead and measurable benefit. Define agent manifest with mission, owner, permissions, interfaces, evidence and retirement criteria.

## Session/project synchronisation protocol — proposed
1. At the start of a new BEEXCITED project or session, read **PROJECT-LAUNCH-Plus.md**, this file, and the project's own current SSSOT issue/branch/readme.
2. Treat project-specific tested baselines as authoritative for code and runtime behavior; global architecture provides shared direction, not permission to overwrite local verified facts.
3. Note **architecture version/date**, current project ID, flight leg/sprint, last verified baseline, outstanding MU decisions and next authorised action.
4. After a material MU-approved architecture decision, update this shared record and link the relevant project issue(s). For project-specific results, update the project record first; promote reusable lessons here after evidence review.
5. Do not assume other live chat threads automatically received an update. On handover/resume, retrieve the current GitHub record. Where no GitHub access is available, ask for the latest text or link.
6. Mark claims **APPROVED PRINCIPLE / PROPOSED DESIGN / TESTED / VERIFIED / SUPERSEDED**; avoid silent promotion of proposals into implementation.
7. Keep sync lightweight: no repetitive full-document copying into every project issue. Link canonical records and maintain a short local delta.
